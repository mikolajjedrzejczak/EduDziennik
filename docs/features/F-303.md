# F-303 — User Creation

## 1. Status

Planned

## 2. Priorytet

P0

## 3. Cel

Tworzyć konto i opcjonalny kontekst dydaktyczny.

## 4. Historia użytkownika

Jako administrator chcę tworzyć konto i opcjonalny kontekst dydaktyczny, aby móc bezpiecznie realizować zadania dziennika.

## 5. Zakres

Formularz roli/statusu/hasła; opcjonalny enrollment studenta lub assignments teachera, jeden commit.

## 6. Zależności

[F-302](F-302.md), [F-306](F-306.md), [F-308](F-308.md), [F-402](F-402.md)

## 8. Uprawnienia

Wyłącznie admin; User/School Policies. Ochrona ostatniego admina i historycznych relacji obowiązuje niezależnie od UI.

## 9. Reguły biznesowe

Teacher bez przypisań dozwolony; student bez klasy ma empty state; email unique także trashed. Szczegóły: [reguły domenowe](../database/BUSINESS_RULES.md).

## 10. Baza danych

users, opcjonalnie enrollments/assignments przez usługi. Zmiany tylko migracjami.

## 11. Implementacja Laravel

Admin/UserController@create; Admin/UserController@store [Pełne trasy](../http/ROUTES.md).

## 12. Kontrakt Inertia

admin/users/create; UserFormProps; redirect admin.users.show [Typy i redirecty](../http/REQUESTS_RESPONSES.md).

## 13. Implementacja React

Strony zgodnie z kontraktem powyżej; komponenty z [COMPONENTS](../design/COMPONENTS.md), useForm dla mutacji, URL dla filtrów. Nie powielać serwisów domenowych w React.

## 14. Tailwind / UI

Semantyczne tokeny [DESIGN_SYSTEM](../design/DESIGN_SYSTEM.md), mobile 390/tablet 1024/desktop 1440 według [RESPONSIVENESS](../design/RESPONSIVENESS.md); stany pending/error/empty i fokus.

## 15. Walidacja

StoreUserRequest — reguły pól w [kontrakcie](../http/REQUESTS_RESPONSES.md).

## 16. Obsługa błędów

[ERROR_HANDLING](../http/ERROR_HANDLING.md): błąd zakresu403/404, walidacja przez redirect/errors; brak częściowego zapisu i automatycznego ponawiania mutacji.

## 17. Przypadki brzegowe

Powtórny email w innej wielkości liter, niezgodna rola relacji, błąd przydziału.

## 18. Bezpieczeństwo

Serwer ponownie sprawdza zakres, także przy bezpośrednim żądaniu. Props tylko z allowlisty; brak haseł i danych obcych kont. Nie ufać can ani hidden input.

## 19. Kryteria akceptacji

**Mając** wymagane zależności i dane testowe, **gdy** wykonano funkcję w opisanym zakresie, **wtedy**: Poprawne dane tworzą konto i relacje atomowo; błąd jednej relacji nie zostawia konta; hasło zahashowane.

**Mając** błędny kontekst lub dane, **gdy** operacja zostanie podjęta, **wtedy** brak nieautoryzowanego efektu i komunikat zgodny z sekcją błędów.

## 20. Testy

Feature transactional create/unique/role injection; E2E admin create→show.

## 21. Definition of Done

Kryteria z sekcji19 udowodnione testami, zależności działają, dokumentacja/kontrakty aktualne; [wspólne DoD](../testing/DEFINITION_OF_DONE.md). Dla brakujących ramek nie deklarować pełnej zgodności wizualnej; rozstrzygnąć lukę przed Done.
