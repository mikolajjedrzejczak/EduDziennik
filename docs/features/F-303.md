## 22. Stan implementacji i odstępstwa od Figmy

FACT: `GET /admin/users/create` (`admin/users/create`, `UserFormProps { user: null, options: { roles, classes, terms, subjects } }`) i `POST /admin/users` (`StoreUserRequest` → `UserService::create`) są wdrożone; po sukcesie redirect do `admin.users.show` z flash `success`. Słowniki to tylko wybieralne rekordy (klasy niearchiwalne, semestry niezamknięte, przedmioty nieusunięte), max 500, przekroczenie → 503.

FACT: konto, opcjonalne `enrollment` ucznia i lista `assignments` nauczyciela powstają w jednej transakcji, z użyciem `EnrollmentService::enroll` i `AssignmentService::assign` (te same blokady i walidacje co F-306/F-308). Błąd dowolnej relacji cofa konto; błędy usług są mapowane na pola `enrollment.*` / `assignments.N.*`. Wyścig na unikalnym e-mailu daje błąd pola `email`, nie 500.

DECISION: odstępstwa od ramek 20:1261/20:1600/24:685/24:807, wynikające z kontraktu i reguł domeny:
- hasło 12–128 znaków (kontrakt `StoreUserRequest`), nie „min. 10”; brak opcji „wymuś zmianę hasła” i „wyślij e-mail” oraz ograniczenia do domeny szkoły — MVP nie ma maili ani wymuszenia zmiany (`REQUESTS_RESPONSES`: brak maila z hasłem); opis nad formularzem mówi o bezpiecznym przekazaniu hasła;
- dodano wybór statusu konta (aktywne/nieaktywne; relacje wymagają aktywnego konta);
- przydział nauczyciela to wiersz przedmiot + klasa + semestr (kontrakt wymaga `term_id`), nie przedmiot + wiele klas; do 20 wierszy, duplikaty odrzucane;
- sekcja „Klasa ucznia” (klasa + daty członkostwa) nie ma ramki — kompozycja z istniejących pól; uczeń bez klasy jest dozwolony;
- sekcja kontekstu pojawia się tylko dla roli ucznia/nauczyciela; wysyłany jest wyłącznie kontekst wybranej roli, a serwer i tak odrzuca niezgodny (`prohibited_unless`).

VERIFIED (kontenery php:8.3 + MariaDB 11.4, node:22): `UserCreationTest` (12 testów: unikalność bez względu na wielkość liter i dla usuniętych, wstrzyknięcie roli, atomowość, hash hasła, odmowy 403/login), Vitest `user-create.test.tsx`, Playwright `user-create.spec.ts` (błędy → poprawka → utworzenie → show, 390/1024/1440, fokus podsumowania błędów, brak poziomego przewijania). OPEN QUESTION: przegląd wizualny z ramkami, test klawiatury poza fokusem podsumowania i ramka tabletu.

## 23. Review #65 — ponowna autoryzacja tworzenia konta (2026-11-17)

FACT: `UserService::create` przed pierwszym zapisem blokuje `domain_locks.admin_membership`, następnie pobiera aktora przez `withTrashed()->lockForUpdate()` i wykonuje `UserPolicy.create` na aktualnym rekordzie. Brak aktora oznacza 403; degradacja, nieaktywność i soft delete są odrzucane przez Policy. Blokady pozostają do końca transakcji konta wraz z enrollmentem/przydziałami. Kolejność blokady domenowej i aktora odpowiada `update`/`delete`; nie zmieniono kontraktu formularza ani schematu bazy.

FACT: `ConcurrentUserCreationTest` używa dwóch procesów, zatwierdzonych fixture i bariery na stdin: `StoreUserRequest.authorize` → zmiana uprawnień przez `UserService.update/delete` i commit → `UserService.create` ze starym ID aktora. Dziewięć wariantów obejmuje role change / inactive / soft delete oraz tworzenie admina / ucznia z enrollmentem / nauczyciela z przydziałem. Odmowa nie pozostawia konta ani relacji. `UserCreationTest` obejmuje sukces aktywnego administratora, w tym tworzenie kolejnego aktywnego admina, oraz rollback konta i wcześniejszych relacji przy błędzie kolejnej relacji.

FACT (kontrola kodu analogicznych ścieżek): `TeacherAssignmentController` wywołuje `AssignmentService.assign/revoke/reactivate`, a `SubjectController` wywołuje `SubjectService.create/rename/archive` bez ID aktora. Te serwisy sprawdzają reguły domenowe, ale nie ponawiają autoryzacji administratora w transakcji. Jest to analogiczna luka wynikająca z kodu, bez próby współbieżnej dla tych ścieżek. PLANNED: osobna poprawka kontraktów serwisów, przekazania aktora z HTTP i testów odmowy pod blokadą; ta zmiana dotyczy tworzenia konta.

Kontrole UI (Figma, Vitest/RTL, Playwright, frontend lint/typecheck/build) pominięto: zmiana dotyczy wyłącznie transakcji backendu, bez zmian widoków, props i formularzy. Status całej funkcji pozostaje bez zmian.

VERIFIED — izolowane kontenery PHP 8.3 i MariaDB 11.4, dedykowana baza `edudziennik_test`: `php artisan test --compact` — 385 testów, 5233 asercje, bez błędów i ostrzeżeń; `vendor/bin/phpstan analyse --no-progress` — bez błędów; `vendor/bin/pint --test` dla czterech zmienionych/dodanych plików PHP — sukces. ## 24. Review #66 — nieprawidłowe typy ID przydziałów (2026-11-17)

FACT: callback `StoreUserRequest.after` kończy się przed deduplikacją, jeśli walidator ma błędy. `implode` otrzymuje ID wyłącznie po przejściu reguł pól; poprawne duplikaty nadal dodają błąd `assignments.N`.

VERIFIED: testy HTTP w `UserCreationTest` obejmują tablicę, obiekt JSON i `null` w każdym z pól `school_class_id`, `subject_id`, `term_id` (9 wariantów). Każde żądanie zawiera również wcześniejszy poprawny przydział; odpowiedź przekierowuje do formularza z błędem konkretnego pola, bez utworzenia konta ani przydziałów. Osobny test potwierdza odrzucenie duplikatu dla tych samych ID przesłanych jako liczby i stringi. Przed poprawką sześć wariantów tablica/obiekt odtwarzało HTTP 500 z `Array to string conversion`.

VERIFIED — izolowane kontenery PHP 8.3 i MariaDB 11.4, dedykowana baza `edudziennik_test`: `php artisan test --compact` — 395 testów, 5302 asercje, bez błędów i ostrzeżeń (w tym `UserCreationTest`: 23 testy, 181 asercji); `vendor/bin/phpstan analyse --no-progress --memory-limit=512M` — bez błędów; `vendor/bin/pint --test` dla obu zmienionych plików PHP i `git diff --check` — sukces.

Kontrole UI (Figma, Vitest/RTL, Playwright, frontend lint/typecheck/build) pominięto: zmiana dotyczy callbacku walidacji backendu, bez zmian widoków i props. Status całej funkcji pozostaje bez zmian; CI nie uruchamiano.
