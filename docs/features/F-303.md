## 22. Stan implementacji i odstępstwa od Figmy

FACT: `GET /admin/users/create` (`admin/users/create`, `UserFormProps { user: null, options: { roles, classes, terms, subjects } }`) i `POST /admin/users` (`StoreUserRequest` → `UserService::create`) są wdrożone; po sukcesie redirect do `admin.users.show` z flash `success`. Słowniki to tylko wybieralne rekordy (klasy niearchiwalne, semestry niezamknięte, przedmioty nieusunięte), max 500, przekroczenie → 503.

FACT: konto, opcjonalne `enrollment` ucznia i lista `assignments` nauczyciela powstają w jednej transakcji, z użyciem `EnrollmentService::enroll` i `AssignmentService::assign` (te same blokady i walidacje co F-306/F-308). Błąd dowolnej relacji cofa konto; błędy usług są mapowane na pola `enrollment.*` / `assignments.N.*`. Wyścig na unikalnym e-mailu daje błąd pola `email`, nie 500.

DECISION: odstępstwa od ramek 20:1261/20:1600/24:685/24:807, wynikające z kontraktu i reguł domeny:
- hasło 12–128 znaków (kontrakt `StoreUserRequest`), nie „min. 10”; brak opcji „wymuś zmianę hasła” i „wyślij e-mail” oraz ograniczenia do domeny szkoły — MVP nie ma maili ani wymuszenia zmiany (`REQUESTS_RESPONSES`: brak maila z hasłem); opis nad formularzem mówi o bezpiecznym przekazaniu hasła;
- dodano wybór statusu konta (aktywne/nieaktywne; relacje wymagają aktywnego konta);
- przydział nauczyciela to wiersz przedmiot + klasa + semestr (kontrakt wymaga `term_id`), nie przedmiot + wiele klas; do 20 wierszy, duplikaty odrzucane;
- sekcja „Klasa ucznia” (klasa + daty członkostwa) nie ma ramki — kompozycja z istniejących pól; uczeń bez klasy jest dozwolony;
- sekcja kontekstu pojawia się tylko dla roli ucznia/nauczyciela; wysyłany jest wyłącznie kontekst wybranej roli, a serwer i tak odrzuca niezgodny (`prohibited_unless`).
