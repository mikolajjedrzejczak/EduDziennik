# F-305 — User Deletion

## 1. Status

In review — implementacja zweryfikowana lokalnie, adaptacje UI do przeglądu

## 2. Priorytet

P0

## 3. Cel

Logicznie usunąć konto bez usunięcia ocen.

## 4. Historia użytkownika

Jako administrator chcę logicznie usunąć konto bez usunięcia ocen, aby móc bezpiecznie realizować zadania dziennika.

## 5. Zakres

Dialog z nazwiskiem potwierdzenia, soft delete, status inactive, sesje unieważnione.

## 6. Zależności

[F-304](F-304.md)

## 8. Uprawnienia

Wyłącznie admin; User/School Policies. Ochrona ostatniego admina i historycznych relacji obowiązuje niezależnie od UI.

## 9. Reguły biznesowe

Nie self, nie ostatni active admin; email zarezerwowany; audyt ocen zachowany. Szczegóły: [reguły domenowe](../database/BUSINESS_RULES.md).

users.deleted_at/status, sessions, domain_locks. Zmiany tylko migracjami.

## 13. Implementacja React

Semantyczne tokeny [DESIGN_SYSTEM](../design/DESIGN_SYSTEM.md), mobile 390/tablet 1024/desktop 1440 według [RESPONSIVENESS](../design/RESPONSIVENESS.md); stany pending/error/empty i fokus.

## 15. Walidacja

DeleteUserRequest — reguły pól w [kontrakcie](../http/REQUESTS_RESPONSES.md).

## 16. Obsługa błędów

[ERROR_HANDLING](../http/ERROR_HANDLING.md): błąd zakresu403/404, walidacja przez redirect/errors; brak częściowego zapisu i automatycznego ponawiania mutacji.

## 17. Przypadki brzegowe

Anulowanie, literówka nazwiska, ostatni admin, nauczyciel będący aktorem audytu.

## 18. Bezpieczeństwo

Serwer ponownie sprawdza zakres, także przy bezpośrednim żądaniu. Props tylko z allowlisty; brak haseł i danych obcych kont. Nie ufać can ani hidden input.

## 19. Kryteria akceptacji

**Mając** wymagane zależności i dane testowe, **gdy** wykonano funkcję w opisanym zakresie, **wtedy**: Po potwierdzeniu konto znika z aktywnej listy i nie loguje się, lecz wcześniejsze oceny/audyty pozostają.

**Mając** błędny kontekst lub dane, **gdy** operacja zostanie podjęta, **wtedy** brak nieautoryzowanego efektu i komunikat zgodny z sekcją błędów.

## 20. Testy

Feature concurrent last admin i FK retention; E2E delete/cancel/deny.

## 21. Definition of Done

Kryteria z sekcji19 udowodnione testami, zależności działają, dokumentacja/kontrakty aktualne; [wspólne DoD](../testing/DEFINITION_OF_DONE.md). Dla brakujących ramek nie deklarować pełnej zgodności wizualnej; rozstrzygnąć lukę przed Done.

## 22. Realizacja — 2026-11-15

FACT: wdrożono `DeleteUserRequest`, `UserController.destroy`, `UserService.delete`, trasę DELETE i wspólny `DeleteUserDialog` na liście oraz szczegółach konta. Użyto istniejących SoftDeletes, tabel sessions/domain_locks, indeksu unique e-mail i historycznych relacji `withTrashed`; bez migracji i nowych zależności.

FACT: transakcja współdzieli stałą blokadę `admin_membership` z F-304, ponownie odczytuje i autoryzuje aktora, blokuje User według ID i sprawdza aktualne nazwisko. Ustawia inactive/deleted_at, rotuje remember token i usuwa sesje celu. Nie kasuje ocen, audytów, enrollmentów ani assignmentów. Nie można usunąć siebie; równoczesne usuwanie/dezaktywacja nie odbiera ostatniego aktywnego admina. Ponowny DELETE daje 404, nazwisko z literówką redirect/errors, brak częściowego zapisu po awarii unieważniania sesji. E-mail pozostaje zarezerwowany.

DECISION — adaptacja ramek `19:1067` i `24:1044` odczytanych przez Figma MCP (design context i screenshot):

- Desktop: dialog 480 px, metadane rola/e-mail/status, odstępy 24 px i stopka na surface-secondary; mobile: dolny arkusz z uchwytem, zamknięciem, kontrolkami 48 px, przyciskiem usunięcia nad anulowaniem i safe area. Public Sans, istniejące tokeny i Lucide Trash/X odpowiadają opisanym komponentom Figmy.
- Użyto aktualnego nazwiska i imienia bez automatycznego odmieniania nazw osobowych. Tekst nie zawiera fikcyjnej liczby ocen ani deklaracji prawnej retencji z makiety — zgodnie z BR-06 mówi o zachowaniu ocen i historii. Dane podsumowania pochodzą wyłącznie z istniejącego UserDTO.
- Ten sam dialog działa z listy i szczegółów. Szczegóły są istniejącą udokumentowaną adaptacją F-302; tło listy/szczegółów nie jest w tym zadaniu przebudowywane. Nie odtworzono systemowego paska telefonu.
- Nie ma dedykowanej ramki F-305 dla tabletu. 1024 px to adaptacja desktopowego dialogu według RESPONSIVENESS; 320 px to dodatkowy reflow. Nie deklarujemy zgodności pikselowej ani istnienia brakującej ramki.
- Radix zapewnia semantykę dialogu i ograniczenie fokusu; początkowy fokus trafia do nazwiska, Escape/Anuluj wraca do przycisku otwarcia. Pending blokuje ponowny zapis i zamknięcie, błędy mają podsumowanie i opis pola. Nie dodano automatycznego ponawiania żądania.
